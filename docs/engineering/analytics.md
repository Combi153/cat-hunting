## 코드 연결

빌드 환경에 `VITE_GA_MEASUREMENT_ID=G-실제측정ID`를 설정하고 다시 빌드한다. 배포 환경에도 같은 변수가 필요하다. Vite는 빌드 시 값을 번들에 넣으므로 이미 만들어진 파일에 환경 변수만 추가해서는 적용되지 않는다.

로컬에서는 `.env.example`을 `.env.local`로 복사해 설정한다. 개발 서버는 기본적으로 수집하지 않는다. 테스트 속성과 `VITE_GA_DEBUG=true`를 함께 설정하면 로컬 DebugView 검증이 가능하다. 운영 환경에서는 DEBUG를 켜지 않는다. ID가 없거나 잘못되면 외부 스크립트와 이벤트 전송 모두 비활성이다. 분석 스크립트가 차단되어도 게임은 진행된다.

측정 ID는 공개 식별자다. 광고 개인화와 Google Signals는 코드에서 끈다. 플레이 이벤트에는 이름·이메일·입력 문구를 넣지 않는다. GA의 기본 방문 분석과 식별 방식은 별도로 적용된다.

## 수집하는 내용

| 이벤트 | 의미 |
| --- | --- |
| 기본 GA 방문 이벤트 | 방문자·세션·유입 경로·기기 |
| `level_load` / `level_load_error` | 시작 버튼 이후 시험실 준비 시도/실패 |
| `level_start` | 실제 시험 시작. `start_source`는 `lobby`, `retry`, `advance` |
| `first_inspection` | 해당 판에서 처음 학생을 선택함. 도착 완료를 의미하지 않음 |
| `student_report` | 신고 성공/오인 (`report_result`) |
| `help_complete` | 답안지/커튼 도움 완료 (`help_type`) |
| `level_progress` | 게임 시간 15초·30초 체크포인트 |
| `level_end` | 결과 확정. `success`와 `end_reason`의 `win`, `health`, `missed`로 구분 |
| `level_exit` | 사용자가 그만두기를 확인하고 로비로 돌아감 |
| `level_background` | 진행 중 탭을 숨김. 일시 중단일 수 있어 이탈로 확정하지 않음 |

플레이 이벤트에는 단계(`level_name`: `exam_1`~`exam_5`), 규칙 버전(`ruleset`), 판 식별자(`attempt_id`), 현재 페이지 내 단계별 도전 순서(`attempt_number`), 실제 게임 진행 초, 남은 체력, 적발/미검거/오인 신고/도움 지연/과도한 관찰/도움 완료/학생 선택 횟수를 보낸다. 도전 순서는 새로고침 시 초기화되므로 생애 첫 도전 횟수로 해석하지 않는다.

`level_start`, `level_end`는 [GA4 게임 권장 이벤트](https://developers.google.com/analytics/devguides/collection/ga4/reference/events#level_end)를 사용한다.

## 처음 볼 보고서

- **방문 규모:** 사용자 획득·트래픽 획득에서 사용자 수, 세션, 유입 경로를 본다. 이벤트 수는 사람 수가 아니다.
- **단계별 실패:** 탐색 자유 형식에서 `level_end`를 필터링하고 단계 × 종료 사유별 이벤트 수를 본다. 완료된 판 기준 실패율은 `(health + missed) / 전체 level_end`다. 미완료 판은 분모에 들어가지 않는다.
- **진행 퍼널:** `level_start(exam_1)` → `level_end(exam_1, win)` → `level_start(exam_2)` 순으로 다섯 단계까지 구성한다. 사용자 단위 퍼널로 어느 단계에서 다음 단계로 진행하지 않는지 확인한다.
- **원인:** 실패 판의 오인 신고·도움 지연·과도한 관찰·미검거 수와 경과 시간을 비교한다. 체력 소진 자체는 마지막 원인 하나를 뜻하지 않으므로 누적 원인을 함께 본다.
- **재도전:** `level_start` 중 `start_source=retry`를 단계별로 본다. 실패 직후 결과 화면의 재도전만 이 값이며 로비를 경유한 재시작은 `lobby`다.

탭 닫힘·모바일 강제 종료는 전송을 보장할 수 없다. 시작만 있고 종료가 없는 판은 미완료 추정이며 실패와 합치지 않는다. 정확한 판별 이탈 분석은 BigQuery에서 `attempt_id`를 기준으로 시작/종료/명시적 그만두기를 연결하고 관찰 기간을 정해서 계산한다. GA 탐색의 사용자 퍼널과 판별 완료율은 다른 지표다. 광고 차단 등으로 수집된 사용자는 실제 방문자보다 적을 수 있다.

## GA에 등록한 항목

2026-11-18에 관리 → 데이터 표시 → 맞춤 정의에서 이벤트 범위 측정기준 6개를 등록했다: 시험 단계(`level_name`), 종료 사유(`end_reason`), 시작 경로(`start_source`), 규칙 버전(`ruleset`), 신고 결과(`report_result`), 도움 종류(`help_type`).

## 결과·공유·다시보기·소품·배너 확장 (2026-11-18)

게임 UI를 바꾸지 않고 다음 이벤트를 추가했다. 개발·미리보기 운영 GA 비활성 정책을 유지한다.

| 이벤트 | 범위와 해석 |
| --- | --- |
| `result_action` | 결과에서 retry/advance/home/review/share 선택. 한 판에서 여러 선택이 가능하므로 합계를 완료 판 수로 해석하지 않는다. |
| `review_open` | 실패 결과에서 다시보기 열기 |
| `review_view` | 소품 한 학생을 보는 구간 종료. 이전/다음·닫기·탭 숨김에서 전송하고 `review_seconds`는 숨김 시간을 제외한다. 재방문과 탭 복귀는 별도 구간이므로 이벤트 수는 학생 수나 다시보기 횟수가 아니다. |
| `share_result` | `interaction_action=native/copy`, `interaction_status=attempt/resolved/cancelled/error/unsupported/copied/manual_required`. OS 응답 resolved는 상대방 전달 완료가 아니다. 직접 복사 안내 이후 사용자가 실제 복사했는지는 알 수 없다. 결과를 떠난 뒤 늦게 온 응답은 버린다. |
| `prop_result` | 완료된 판에서 배치된 소품 종류마다 1회. 범인/정상 학생 배치 수와 적발/미검거/오인 수. 중도 포기 판은 제외한다. |
| `banner_click` | 생각하는 공간 배너를 누름. `banner_placement=lobby/result`, `banner_id=thinkplace`. 클릭 수이며 노출 수·CTR·목적지 방문 완료가 아니다. 기존 GA 자동 outbound `click`과 합산하지 않는다. |

결과 이후 이벤트는 종료 판의 `attempt_id`, 단계, 규칙, 종료 사유를 유지한다. 저장 데이터·정답 화면·게임 진행에는 영향을 주지 않으며 이메일·학생 좌석·랜덤 seed·공유 문구·대화 상대·오류 원문은 보내지 않는다.

`prop_type`은 glasses/ear/camera/watch/pen/note다. `prop_result`만 필터링하고 다음처럼 계산한다.

- 적발 비율 = `caught_count / culprit_count`, 미검거 비율 = `missed_count / culprit_count`.
- 정상 학생 배치 대비 오인 비율 = `false_report_count / normal_count`.
- 분모는 실제 화면에서 관찰한 횟수가 아니라 해당 판에 배치된 학생 수다. 조기 생명 소진도 미검거에 영향을 준다. 단계·규칙·배포 버전을 나누어 비교하며 0인 분모는 비율을 계산하지 않는다.
- 기존 `level_end` 누적 수와 `prop_result` 수는 같은 판을 설명하므로 섞어 합산하지 않는다.

같은 페이지에서 직전 완료 판과 같은 단계를 다시 시작하면 `previous_review=yes/no`를 플레이 이벤트에 붙인다. 다른 단계·첫 시작·새로고침은 `not_applicable`이다. 로비 경유 재시작도 연결하지만 영구 사용자 이력은 아니다. `result_action`의 같은 필드는 현재 결과에서 다시보기를 이용했는지를 뜻한다. 다시보기 이용자의 다음 판 성공률 비교는 선택 편향이 있으므로 학습 효과의 인과관계를 입증하지 않는다.

모든 명시적 이벤트에 `build_version`(Git SHA 앞 12자리)을 추가한다. Vercel 빌드에서는 `VERCEL_GIT_COMMIT_SHA`, 로컬에서는 Git HEAD를 사용한다. 로컬 미커밋 변경까지 식별하는 값은 아니다.

## 재도전 제한·공유 보상 (2026-11-18)

- `retry_exhausted`: 실패 결과 확정 후 잔액이 0인 경우. 종료 판의 문맥과 `retry_remaining=0`을 보낸다. 잠금 화면을 본 고유 사람 수나 확정 이탈 수는 아니다.
- `retry_reward`: 기본 공유 성공 응답 또는 복사 성공 후, 화면이 보이는 상태에서 5초 대기를 완료해 3회를 실제 지급한 경우. `interaction_action=native/copy`, 지급 후 `retry_remaining`을 보낸다. 일일 보상 제한은 없고 전달 완료를 의미하지 않는다.
- 기존 `share_result`는 이제 로비에서도 발생한다. 로비 공유/보상에는 `share_placement=lobby`를 사용하고 이전 결과의 `attempt_id`를 붙이지 않는다. 결과 공유/보상은 종료 판의 문맥을 유지한다.
- 기존 `nyangijapgi.v2` 기록·플레이 이벤트 의미는 유지한다. 새 맞춤 정의나 GA 대시보드는 이번 작업에서 수정하지 않았다. 공유 클릭·보상 수만으로 바이럴 효과를 입증하지 않으며, 개인 초대 코드에 따른 친구 유입 귀속은 구현하지 않았다.

### 모달·공유 대기 변경 이후 해석 (2026-11-18)

결과의 `result_action=share`는 공유 안내를 열었다는 뜻이고, 실제 `share_result`의 native/copy attempt는 안내 안 ‘공유하기’를 누른 시점이다. 0회 도전은 `result_action=retry` 뒤 공유 안내로 이어질 수 있으므로 실제 시험 시작은 `level_start`로 확인한다. 보상은 성공 응답·복사 성공 뒤 5초의 가시 대기가 끝나야 `retry_reward`로 집계된다. 안내 열기·성공 응답만으로 보상/전달 완료를 추정하지 않는다. 이벤트 이름·맞춤 정의·GA 대시보드는 바꾸지 않았다.
